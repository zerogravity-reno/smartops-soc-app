What this run exercised

The generations were shaped like real 8B output — markdown emphasis, inline citations, a prose colon, one fabricated id — so the run is a genuine test of the pipeline, not a happy path.

The parser fix — 2 of 3 identity observations recovered

The field terminator was [A-Z][A-Z ]+: under IGNORECASE, which matches any prose line ending in a colon. Identity’s second observation is un-bulleted and reads “The pattern was: …”, so the capture ended there and took the third observation with it.

before  observations = ["bostoll logged on interactively … [auth_events#1]"]
after   observations = ["bostoll logged on interactively … [auth_events#1]",
                        "The pattern was: single logon, no preceding failures [auth_events#1]",
                        "no failed-logon burst precedes the success [auth_events#1]"]

The rationale was truncated the same way, at “Note the following:”. This mattered beyond lossiness: _finalize_finding unions the inline [header_id] citations found inside observations into the finding’s citations, so dropped observations took their citations with them — starving a grounding fix that was already shipped.

The grounding gate — 1 fabricated citation refused

Network cited dns_resolutions#1, which this run never produced. Both the citation and the observation resting solely on it were dropped, and both were logged:

domain=network | dropped 1 invented citation(s) from a finding: dns_resolutions#1
dropped an observation citing only unresolvable id(s): dns_resolutions#1

Worth flagging: the disposition itself still reads malicious. For a hypothesis-shown verdict, _finalize downgrades an ungrounded supports/ refutes to inconclusive; _finalize_finding has no equivalent downgrade for a disposition. Here it is harmless — reputation#1 still resolves, so the finding is grounded — but a finding whose citations all failed would keep a confident disposition with nothing behind it. That asymmetry is not yet decided either way.

Evidence linkage — every kept citation frozen to its rows

citation_evidence is written at finalisation rather than recomputed on read, so a stored finding can be traced to the rows behind it without re-running route(). The ids follow the chain recorded in the evidence-link design note:

task_id : family : toolUseId : index
cli-20260825T100434 : siem : tooluse_xphZd4kUv8vxMKHX7gdbk0 : 0

The trailing index is positional, and whether it should become content-addressed is open question A in that note. Any answer propagates straight into this field.

What crosses the boundary, and what does not

A DomainFinding is the internal audit record. What the Analyst Agent receives is a DomainJudgement — a projection of it. Two shapes because two audiences, rather than one shape whose consumer has to know which fields to ignore.

Stays here — DomainFinding

  • reasoning_trace — documented “persisted for audit, never re-fed”. Putting a model’s private chain-of-thought into a contract handed to another model is exactly re-feeding it.
  • prompt_tokens, generation_tokens — our telemetry; feeds cost reporting.
  • citation_evidence — superseded on the wire by the richer Exhibit.

Crosses — DomainJudgement

  • disposition, confidence, rationale — the judgement and how strongly it is held.
  • observations, citations — what was seen, and where.
  • exhibits — the actual rows, so the consumer can check the judgement without holding the evidence store.

Why this is not HypothesisAssessment

HypothesisAssessment

  • Per-domain unit: AnalystVerdict, carrying a Stance toward the hypothesis
  • Analyst saw the hypothesis
  • Has overall_stance + confidence, decided locally by combine()
  • Unchanged by this work; still the shape that carries a decided stance

HypothesisFindings

  • Per-domain unit: DomainFinding, carrying a Disposition toward the evidence
  • Analyst never saw the hypothesis
  • No hypothesis-level verdict and no combiner — the absence is the contract
  • Deciding supports/refutes is the Analyst Agent’s job, owned elsewhere

The two share four envelope fields (schema_version, task_id, run_id, hypothesis_id) and differ on the two that matter. Kept as separate models rather than one widened model: one shape meaning two things depending on which fields are populated is the ambiguity the tool_family discriminator exists to prevent.
