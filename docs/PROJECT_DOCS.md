## 2026-08-05 — Subtask contract, EDR diagram, backend scaffolding

## Context

First working session on SmartOps (the multi-agent SecOps triage/IR system).
Starting point was an architecture sketch: Seed Normalizer → Context Builder →
Analyst/Triage agent → domain subagents (EDR/NDR/VT/SIEM) → Tool Broker →
Aggregator → case file, with a separate Critic to be built later. Stack:
Python, Pydantic v2, asyncio, Strands framework for the agent layer.

Working task-by-task rather than building the whole pipeline at once. This
session covered the first task: **the subtask/mission contract** — the format
handed to a subagent and the format it returns.

## Decisions

- **Top-level layout**: `backend/`, `frontend/`, `contracts/`. `contracts/`
  was carved out separately from `backend/` because the mission/result shapes
  are consumed by more than one side (subagents now, the Critic and possibly
  the frontend case-viewer later) — not backend-internal.
- **Packaging**: a `uv` workspace rooted at the project root, Python 3.13
  pinned (`.python-version`). `contracts` and `backend` are each their own
  installable package (`smartops-contracts`, `smartops-backend`), with
  `backend` depending on `contracts` via `[tool.uv.sources]` workspace
  linkage rather than a path hack.
- **Mission contract deviates from the original draft in one structural way**:
  split the subagent's output into two types instead of one.
  - `SubagentAnswer` — the only shape the LLM is forced into via structured
    output (`status`, `summary`, `citation_ids`, `error`). No `task_id`, no
    raw evidence — the model never authors data it didn't actually observe.
  - `SubtaskResult` — assembled by code via `SubtaskResult.from_answer(...)`,
    adds `task_id` and the `evidence` the subagent's own tool-call loop
    collected. This is the only object that ever leaves a subagent.
  - This resolves a contradiction in the original spec (evidence written by
    subagents vs. the case file only ever written sequentially by the
    aggregator) — evidence now just rides along as data on the returned
    object; nothing shared gets touched until the aggregator runs.
- **Validation added beyond the original spec**: `time_window` must be
  timezone-aware with `start < end`; `status == error` iff `error` is set
  (shared by both `SubagentAnswer` and `SubtaskResult`); every `citation_id`
  on a `SubtaskResult` must resolve to an `Evidence` id actually attached to
  it. All three are enforced as Pydantic validators, not conventions.
- **`SubtaskStatus.rejected`** given an explicit meaning: mission was
  unworkable for that domain, no tool call ever attempted or budget-charged —
  distinct from `error` (attempted, failed, retries exhausted).
- The mission/result contract is **data, not a prompt**. `SubagentMission`
  carries no natural-language template. Each subagent module (`edr_agent.py`
  etc., not yet built) owns its own static system prompt and folds the
  mission's `goal` / `scope` / `context` into it at call time. This is what
  lets the Analyst dispatch an arbitrary number of missions per round
  (`run_round()` fans out via `asyncio.gather`) — missions are cheap,
  stateless data objects, gated only by the one shared `Budget`, not by
  anything in the contract itself.

## What we built

- `contracts/` package: `Scope`, `SubagentMission`, `SubtaskStatus`,
  `Evidence`, `SubagentAnswer`, `SubtaskResult` in `src/contracts/subtask.py`.
- `contracts/tests/test_subtask.py` — 15 passing tests covering valid/invalid
  construction, the status/error validator, and the citation→evidence
  validator.
- `backend/` package scaffolded (`src/smartops/`, `src/smartops/subagents/`)
  and wired into the workspace, depending on `smartops-contracts`. No
  implementation code yet — just the home for the next tasks.
- An interactive diagram (published as a Claude artifact) walking one EDR
  mission end to end: the mission-in/result-out shapes with click-to-expand
  explanations per box, plus a Mermaid sequence diagram showing the same
  round over time (budget charged per attempt, the retry, the structured-
  output boundary).

## Open items / next up

Per the original task breakdown, still to build:

1. `budget.py` — shared `Budget` (asyncio.Lock + counter, atomic `charge()`).
2. `subagents/edr_agent.py`, `ndr_agent.py`, `vt_agent.py` — domain-specific,

4. Tests for budget (concurrency safety) and the aggregator write-race

## Tool Execution Method — research findings

Dispatched a Haiku research agent against the Strands Agents SDK docs to
answer: native tool definitions vs. MCP servers, for our subagent design
(each subagent derives and executes its own tool call, retries capped at
2, forces a final answer through structured output; Budget gates spend
across everything).

**The framing on the Asana card ("either...or") is a false binary** — a
single Strands `Agent` can mix native `@tool` functions and MCP-server
tools in the same `tools=[]` list. Key findings:

- **Native tools**: `@tool` decorator, auto-generates JSON schema from type
  hints + docstring. Errors don't crash the loop — they flow back into
  conversation history for the model to react to. No built-in retry.
- **MCP tools**: `MCPClient` implements the same `ToolProvider` interface
  native tools use, so it drops into `Agent(tools=[...])` directly.
  Supports stdio (local) and Streamable HTTP (remote) transports; multiple
  MCP clients can be attached to one agent.
- **Structured output** (`agent.structured_output(SubagentAnswer)`) works
  fine after tool use mid-conversation, and has its own automatic
  retry-on-validation-failure loop, independent of model-call retries.
  Directly validates the `SubagentAnswer`/`SubtaskResult` split from the
  contract task.
- **No built-in tool-call retry** — matches (doesn't fight) our own
  "repair and retry, capped at 2" design; that logic is squarely ours to
  write regardless of native-vs-MCP.
- **"Agents-as-Tools" pattern** matches our Analyst → Subagent shape:
  pass a specialist `Agent` as a tool to a supervisor `Agent`; context
  resets per call by default (good — subagents shouldn't inherit the
  Analyst's history) unless `preserve_context=True`.
- **AWS AgentCore Gateway** is a separate, optional managed MCP-aggregator
  service, not a Strands requirement — standalone `MCPClient` works
  without it. Whether it works with non-Runtime-deployed Strands agents is
  undocumented. Not worth deciding now; revisit only if/when we deploy on
  AgentCore Runtime.

**Two flagged ambiguities in Strands' own docs** (not blockers, just
things to verify empirically once we build against them):
- Whether `structured_output()`'s automatic retry shares a budget with
  model-call retries, or is independent.
- MCPClient retry/backoff configuration on connection failure (open
  upstream issue referenced in the research).

**Shape that falls out of this** (proposed, not yet confirmed by the
user): native `@tool` functions for our own control-plane logic (Budget
`reserve()`/`settle()` calls, bookkeeping), MCP for the actual external
EDR/NDR/VT/SIEM integrations. This also lines up with Mariam's Task Broker
Agent card, which already assumes an MCP gateway on the tool-discovery
side — worth confirming with her rather than deciding in isolation.

## Observability/traceability/cost-tracking — research findings

Dispatched a Haiku research agent (web-grounded, not memory) scoped
explicitly as *complementing* the existing `Budget` ledger, not replacing
it. Findings, not a decision — nothing below is adopted yet.

- **Tracing**: OTel's GenAI semantic conventions (`gen_ai.*` span
  attributes) are now stable. **Strands Agents SDK has this built in** —
  auto-emits spans for agent steps, LLM calls, and tool invocations with no
  manual instrumentation, exportable via OTLP to X-Ray/CloudWatch/
  Jaeger/Datadog/etc.
- **Traceability**: attach `task_id`/`hypothesis_id` as root-span
  attributes; `contextvars` propagate automatically through
  `asyncio.gather()`, so subagent fan-out traces correctly for free. Real
  gap: **MCP has no native trace-context propagation** (open upstream
  issue) — needs a community shim (`opentelemetry-instrumentation-mcp`) or
  manual injection via the JSON-RPC `_meta` field to carry a trace across
  an MCP client→server call.
- **Error handling**: no industry-standard error-code enum exists, but the
  converging pattern is a structured object (`error_code`, `error_type`,
  `severity`, `retry_eligible`) instead of a bare string, so retry logic
  can distinguish "malformed args, retry" from "budget exhausted, stop."
  Our `Budget.reserve()` gate already prevents the worst failure mode
  (silent infinite retry on exhaustion); the open suggestion is just to
  give exhaustion its own explicit code rather than a generic one.
- **Cost tracking**: confirms `reserve()`/`settle()` already *is* the
  standard reconciliation pattern (estimate → gate → actual → reconcile).
  The only addition backends layer on: mirror `cost.estimated`/
  `cost.actual` as span attributes so cost shows up inline in a trace, not
  only in the ledger.
- **Backends surveyed**: Langfuse (open-source, OTel-native, low-effort
  self-host), Arize Phoenix (open-source, OTel-first, low-effort
  self-host), AWS CloudWatch GenAI Observability (managed, ~zero-config if
  already on Strands/Bedrock), Datadog LLM Observability (managed, medium
  effort, pulls real invoices for reconciliation). Helicone flagged as a
  risk, not a pick — acquired by Mintlify, in maintenance mode.
- **Complexity ladder proposed** (tiers, not a recommendation):
  1. Structured JSON logs + existing Budget ledger — no new infra.
  2. OTel spans (Strands emits these for free) → self-hosted Langfuse or
     Phoenix — real trace visualization, no vendor lock-in.
  3. Same OTel → managed backend (Datadog/CloudWatch) — adds invoice
     reconciliation + pre-built eval dashboards, real $ cost.
  4. + LLM-judge evaluators over every trace — only worth it at real
     scale; flagged as carrying real technical debt.

**Not yet decided**: which tier to start on. Given the team's "simple is
best" motto, tier 1 or 2 is the obvious starting range, and tier 2 is
cheaper than it sounds since Strands already emits the spans — adopting it
would mean pointing an OTLP exporter at a self-hosted Langfuse/Phoenix
rather than writing instrumentation by hand. Still needs actual team
discussion before committing.

## 2026-08-09 — Subtasks Planner — scope, Task Broker boundary, structured_output correction

## Context

Continuing from the 08-06 session (Tool Execution Method). Working through the
next Aug-13 task, **Subtasks Planner** — "breaks the received tasks into
subtasks classified by the capability of each subagent." Most of this session
was resolving what that sentence actually means before writing any code.

## Decisions

- **Task Broker Agent (Mariam's card) vs. Subtasks Planner boundary,
  resolved**: reading Task Broker Agent's and Analyst Agent's actual card
  notes surfaced an apparent conflict with the already-built `SubagentMission`
  contract (subagent self-executes its own tool calls) — Task Broker's notes
  read as "execute the tools ... gather the raw events ... dispatch the
  results to the subagent to analyze," which sounded like *it* calls tools
  and subagents only analyze pre-fetched data. Confirmed with the user: that's
  not the intent. The actual division of labor:
  1. Analyst Agent → `AnalystTask` (tool-agnostic: goal + scope only).
  2. **Subtasks Planner** (this task) → classifies the task into
     `SubagentMission`s, one per relevant `ToolFamily`. Owns *only* this
     decision.
  3. **Task Broker Agent** → for each mission's `ToolFamily`, resolves
     "available tools to use" by querying the MCP gateway live. This is the
     dynamic equivalent of what `tools/registry.py`'s static `FAMILY_REGISTRY`
     does today.
  4. **Subagent** → builds its own `Agent(tools=<resolved tools>)` and
     self-executes, per the existing `SubagentMission` contract and the
     08-06 Tool Execution Method decision. Unchanged.
- **`AnalystTask` added as a new contract** (`contracts/analyst_task.py`) —
  the Analyst's "Task description" (question/goal + entity + time window,
  explicitly no product/index/field names) didn't have a type yet. Modeled as
  `task_id` + `hypothesis_id` + `goal` + `scope: Scope` — reuses `Scope`
  rather than inventing new entity/time-window fields.
- **Classification is LLM-driven, not rule-based** — decided explicitly, not
  defaulted to. A rule table would need typed entities (e.g. `file_hash`,
  `host`, `ip`) to key off, and that depends on Yousef's **Context Contract
  Template**, which doesn't exist yet and has no committed date. Rather than
  block this task on someone else's undelivered schema, `TaskClassification`
  (forced structured output: `tool_families: list[ToolFamily]`, `rationale:
  str`) is classified from the task's `goal` text directly. Revisit if/when
  typed entities land — a rule table would be cheaper and worth swapping in
  then.
- **Empty `tool_families` is a valid classification result**, not an error —
  the task may be unworkable for every domain the system currently knows
  about. Distinct from `SubtaskStatus.rejected`, which is a subagent's verdict
  on a mission it actually received; the Planner just emits zero missions.
- **Correction to the 08-06 session doc**: it said `structured_output()` "has
  its own automatic retry-on-validation-failure loop, independent of
  model-call retries." Checked against the actually-installed
  `strands-agents==1.50.2` source (not just docs, which didn't have this
  detail):
  - `Agent.structured_output()` / `structured_output_async()` are
    **deprecated** as of this version — both raise a `DeprecationWarning`
    pointing at the `structured_output_model` parameter on `Agent.__call__()`
    / the `Agent` constructor instead. `planner.py` uses the current API.
  - Structured output is implemented as a **forced tool call**
    (`StructuredOutputTool`, `tool_choice={"any": {}}`). A validation failure
    doesn't trigger a distinct retry subsystem — it comes back as an ordinary
    tool `status: "error"` result, and **the model's own loop decides whether
    to retry**, same as recovering from any other tool error. No fixed retry
    cap specific to structured output.
  - Token usage lives on `AgentResult.metrics.accumulated_usage`, a dict with
    **camelCase Bedrock/Converse-style keys** (`inputTokens`, `outputTokens`,
    `cacheReadInputTokens`, `cacheWriteInputTokens`) — not the snake_case
    `Usage` shape `Budget` already uses. `accumulated_usage` is cumulative
    over the `Agent` instance's *entire lifetime*, not just the last call, so
    reusing one long-lived planner `Agent` across rounds would leak prior
    calls' usage into every later `Budget.settle()`.

## What we built

- `contracts/src/contracts/analyst_task.py` — `AnalystTask`, `TaskClassification`.
- `contracts/tests/test_analyst_task.py` — valid/invalid construction, empty
  `tool_families` accepted, no-tool-specific-fields regression guard (same
  pattern as the existing `SubagentMission` guard).
- `backend/src/smartops/planner.py` — `plan_missions()`:
  - Reserves budget under `role="planner"` before calling the model; returns
    `[]` immediately (no model call) if the reservation fails.
  - `default_classifier(model)` constructs a **fresh `Agent` per call** —
    the fix for the accumulated-usage lifetime issue above.
  - `_usage_from_accumulated()` is the one place that translates Strands'
    camelCase usage dict into `Budget.Usage`.
  - `classify` is injectable (`Classifier` protocol) so tests never touch the
    real Strands SDK or make a model call.
  - Derives each mission's `task_id` as `f"{task.task_id}:{family}"`, so
    `Budget.spend_by_task()` and `run_round()`'s per-mission `asyncio.gather`
    fan-out both get a unique key per subagent dispatch even though every
    mission traces back to one Analyst task.
- `backend/tests/test_planner.py` — 8 tests: multi-family fan-out, derived
  task_id uniqueness, empty-classification → no missions, budget-exhausted →
  no missions and classifier never called, usage translation + ledger
  correctness, missing `structured_output` raises.
- All 47 tests pass (24 contracts + 23 backend) when run scoped to each
  project's own `pyproject.toml` (`cd backend && uv run pytest tests`, not
  from the workspace root — see gotcha below).

## Gotcha, not caused by this session's changes

Running `pytest` from the workspace root does **not** pick up `backend/
pyproject.toml`'s `[tool.pytest.ini_options]` (`asyncio_mode = "auto"`), so
every `async def` test fails with "async def functions are not natively
supported" when invoked that way — pytest resolves its config/rootdir from
the top-level `pyproject.toml`, which has none. Pre-existing, not introduced
here; just confirmed by running the full suite both ways. Always invoke
scoped to the project directory (`cd backend && uv run pytest tests`, `cd
contracts && uv run pytest tests`) until/unless the workspace root gets its
own `[tool.pytest.ini_options]`.

User explicitly asked for a single `Agent` dispatch (`coderabbit:code-reviewer`

**10 findings, all fixed same session, all covered by new tests — 60/60
passing (24 contracts + 33 backend, was 47 before this round):**

1. `registry.py::tools_for()` used an `MCPClient` via `list_tools_sync()`
   without ever calling `.start()` — guaranteed crash the moment any family's
   MCP factory returns a real client. **Fixed**: new `_started_clients`
   cache + `_clients_for()` starts and caches one client per family.
2. `planner.py` reserved budget against `max_output_tokens` but nothing on
   the real call enforced it. **Fixed**: `default_classifier()` now passes
   `Limits(output_tokens=...)` — a soft cap per Strands' own semantics, noted
   as such rather than oversold.
3. A raised exception during classification leaked the budget reservation
   permanently. **Fixed**: new `Budget.release()`, wrapped in try/except in
   `plan_missions()`.
4. The classify call blocked the whole event loop for its duration (Strands'
   `Agent.__call__` blocks its calling thread via `run_async()`). **Fixed**:
   wrapped in `asyncio.to_thread(...)`.
5. MCP connections were opened per call, never closed. **Fixed**: same
   `_started_clients` cache as #1 bounds this to one per family, not one per
   mission.
6. Duplicate `tool_families` from the classifier collided on the same
   derived `task_id`. **Fixed**: `dict.fromkeys(...)` dedupes before minting
   missions.
7. `SubtaskResult` had no uniqueness check on `Evidence.id`. **Fixed**: new
   `_evidence_ids_are_unique` validator.
8. `Scope.entities` validated list length, not that each string was
   non-empty. **Fixed**: new `_entities_are_non_empty` field validator.
9. `Budget.estimate_cost()` had no guard against negative token counts
   (would inflate `remaining` instead of consuming it). **Fixed**: explicit
   `ValueError` guard.
10. `telemetry.py::configure_telemetry()`'s idempotency flag wasn't
    thread-safe despite its own docstring's claim. **Fixed**: guarded with a
    `threading.Lock`.

New file: `backend/tests/test_registry.py` (previously zero coverage on that

## Flagged for Agent Development: empty classification needs to be visible, not silent
