<a id="subtask-contract-edr-diagram-backend-scaffolding"></a>
## 2026-08-05 — Subtask contract, EDR diagram, backend scaffolding

## Context

First working session on SmartOps (the multi-agent SecOps triage/IR system).
Starting point was an architecture sketch: Seed Normalizer → Context Builder →
Analyst/Triage agent → domain subagents (EDR/NDR/VT/SIEM) → Tool Broker →
Aggregator → case file, with a separate Critic to be built later. Stack:
Python, Pydantic v2, asyncio, Strands framework for the agent layer.

Working task-by-task rather than building the whole pipeline at once. This
session covered the first task: **the subtask/mission contract** — the format
handed to a subagent and the format it returns.

## Decisions

- **Top-level layout**: `backend/`, `frontend/`, `contracts/`. `contracts/`
  was carved out separately from `backend/` because the mission/result shapes
  are consumed by more than one side (subagents now, the Critic and possibly
  the frontend case-viewer later) — not backend-internal.
- **Packaging**: a `uv` workspace rooted at the project root, Python 3.13
  pinned (`.python-version`). `contracts` and `backend` are each their own
  installable package (`smartops-contracts`, `smartops-backend`), with
  `backend` depending on `contracts` via `[tool.uv.sources]` workspace
  linkage rather than a path hack.
- **Mission contract deviates from the original draft in one structural way**:
  split the subagent's output into two types instead of one.
  - `SubagentAnswer` — the only shape the LLM is forced into via structured
    output (`status`, `summary`, `citation_ids`, `error`). No `task_id`, no
    raw evidence — the model never authors data it didn't actually observe.
  - `SubtaskResult` — assembled by code via `SubtaskResult.from_answer(...)`,
    adds `task_id` and the `evidence` the subagent's own tool-call loop
    collected. This is the only object that ever leaves a subagent.
  - This resolves a contradiction in the original spec (evidence written by
    subagents vs. the case file only ever written sequentially by the
    aggregator) — evidence now just rides along as data on the returned
    object; nothing shared gets touched until the aggregator runs.
- **Validation added beyond the original spec**: `time_window` must be
  timezone-aware with `start < end`; `status == error` iff `error` is set
  (shared by both `SubagentAnswer` and `SubtaskResult`); every `citation_id`
  on a `SubtaskResult` must resolve to an `Evidence` id actually attached to
  it. All three are enforced as Pydantic validators, not conventions.
- **`SubtaskStatus.rejected`** given an explicit meaning: mission was
  unworkable for that domain, no tool call ever attempted or budget-charged —
  distinct from `error` (attempted, failed, retries exhausted).
- The mission/result contract is **data, not a prompt**. `SubagentMission`
  carries no natural-language template. Each subagent module (`edr_agent.py`
  etc., not yet built) owns its own static system prompt and folds the
  mission's `goal` / `scope` / `context` into it at call time. This is what
  lets the Analyst dispatch an arbitrary number of missions per round
  (`run_round()` fans out via `asyncio.gather`) — missions are cheap,
  stateless data objects, gated only by the one shared `Budget`, not by
  anything in the contract itself.

## What we built

- `contracts/` package: `Scope`, `SubagentMission`, `SubtaskStatus`,
  `Evidence`, `SubagentAnswer`, `SubtaskResult` in `src/contracts/subtask.py`.
- `contracts/tests/test_subtask.py` — 15 passing tests covering valid/invalid
  construction, the status/error validator, and the citation→evidence
  validator.
- `backend/` package scaffolded (`src/smartops/`, `src/smartops/subagents/`)
  and wired into the workspace, depending on `smartops-contracts`. No
  implementation code yet — just the home for the next tasks.
- An interactive diagram (published as a Claude artifact) walking one EDR
  mission end to end: the mission-in/result-out shapes with click-to-expand
  explanations per box, plus a Mermaid sequence diagram showing the same
  round over time (budget charged per attempt, the retry, the structured-
  output boundary).

## Open items / next up

Per the original task breakdown, still to build:

1. `budget.py` — shared `Budget` (asyncio.Lock + counter, atomic `charge()`).
2. `subagents/edr_agent.py`, `ndr_agent.py`, `vt_agent.py` — domain-specific,
   each deriving and repairing its own tool calls; stub the real tool/MCP
   wiring for now.
3. `aggregator.py` — `merge_into_case_file()` (pure, sequential) and
   `run_round()` (concurrent dispatch, no case-file write until the whole
   round returns). **`CaseFile` itself still needs a schema** — referenced
   throughout but not yet defined anywhere.
4. Tests for budget (concurrency safety) and the aggregator write-race
   regression (10+ concurrent results → no evidence dropped).

Explicitly still out of scope: the Critic, real MCP tool wiring, model
selection per domain.

## Tool Execution Method — research findings

Dispatched a Haiku research agent against the Strands Agents SDK docs to
answer: native tool definitions vs. MCP servers, for our subagent design
(each subagent derives and executes its own tool call, retries capped at
2, forces a final answer through structured output; Budget gates spend
across everything).

**The framing on the Asana card ("either...or") is a false binary** — a
single Strands `Agent` can mix native `@tool` functions and MCP-server
tools in the same `tools=[]` list. Key findings:

- **Native tools**: `@tool` decorator, auto-generates JSON schema from type
  hints + docstring. Errors don't crash the loop — they flow back into
  conversation history for the model to react to. No built-in retry.
- **MCP tools**: `MCPClient` implements the same `ToolProvider` interface
  native tools use, so it drops into `Agent(tools=[...])` directly.
  Supports stdio (local) and Streamable HTTP (remote) transports; multiple
  MCP clients can be attached to one agent.
- **Structured output** (`agent.structured_output(SubagentAnswer)`) works
  fine after tool use mid-conversation, and has its own automatic
  retry-on-validation-failure loop, independent of model-call retries.
  Directly validates the `SubagentAnswer`/`SubtaskResult` split from the
  contract task.
- **No built-in tool-call retry** — matches (doesn't fight) our own
  "repair and retry, capped at 2" design; that logic is squarely ours to
  write regardless of native-vs-MCP.
- **"Agents-as-Tools" pattern** matches our Analyst → Subagent shape:
  pass a specialist `Agent` as a tool to a supervisor `Agent`; context
  resets per call by default (good — subagents shouldn't inherit the
  Analyst's history) unless `preserve_context=True`.
- **AWS AgentCore Gateway** is a separate, optional managed MCP-aggregator
  service, not a Strands requirement — standalone `MCPClient` works
  without it. Whether it works with non-Runtime-deployed Strands agents is
  undocumented. Not worth deciding now; revisit only if/when we deploy on
  AgentCore Runtime.

**Two flagged ambiguities in Strands' own docs** (not blockers, just
things to verify empirically once we build against them):
- Whether `structured_output()`'s automatic retry shares a budget with
  model-call retries, or is independent.
- MCPClient retry/backoff configuration on connection failure (open
  upstream issue referenced in the research).

**Shape that falls out of this** (proposed, not yet confirmed by the
user): native `@tool` functions for our own control-plane logic (Budget
`reserve()`/`settle()` calls, bookkeeping), MCP for the actual external
EDR/NDR/VT/SIEM integrations. This also lines up with Mariam's Task Broker
Agent card, which already assumes an MCP gateway on the tool-discovery
side — worth confirming with her rather than deciding in isolation.

## Observability/traceability/cost-tracking — research findings

Dispatched a Haiku research agent (web-grounded, not memory) scoped
explicitly as *complementing* the existing `Budget` ledger, not replacing
it. Findings, not a decision — nothing below is adopted yet.

- **Tracing**: OTel's GenAI semantic conventions (`gen_ai.*` span
  attributes) are now stable. **Strands Agents SDK has this built in** —
  auto-emits spans for agent steps, LLM calls, and tool invocations with no
  manual instrumentation, exportable via OTLP to X-Ray/CloudWatch/
  Jaeger/Datadog/etc.
- **Traceability**: attach `task_id`/`hypothesis_id` as root-span
  attributes; `contextvars` propagate automatically through
  `asyncio.gather()`, so subagent fan-out traces correctly for free. Real
  gap: **MCP has no native trace-context propagation** (open upstream
  issue) — needs a community shim (`opentelemetry-instrumentation-mcp`) or
  manual injection via the JSON-RPC `_meta` field to carry a trace across
  an MCP client→server call.
- **Error handling**: no industry-standard error-code enum exists, but the
  converging pattern is a structured object (`error_code`, `error_type`,
  `severity`, `retry_eligible`) instead of a bare string, so retry logic
  can distinguish "malformed args, retry" from "budget exhausted, stop."
  Our `Budget.reserve()` gate already prevents the worst failure mode
  (silent infinite retry on exhaustion); the open suggestion is just to
  give exhaustion its own explicit code rather than a generic one.
- **Cost tracking**: confirms `reserve()`/`settle()` already *is* the
  standard reconciliation pattern (estimate → gate → actual → reconcile).
  The only addition backends layer on: mirror `cost.estimated`/
  `cost.actual` as span attributes so cost shows up inline in a trace, not
  only in the ledger.
- **Backends surveyed**: Langfuse (open-source, OTel-native, low-effort
  self-host), Arize Phoenix (open-source, OTel-first, low-effort
  self-host), AWS CloudWatch GenAI Observability (managed, ~zero-config if
  already on Strands/Bedrock), Datadog LLM Observability (managed, medium
  effort, pulls real invoices for reconciliation). Helicone flagged as a
  risk, not a pick — acquired by Mintlify, in maintenance mode.
- **Complexity ladder proposed** (tiers, not a recommendation):
  1. Structured JSON logs + existing Budget ledger — no new infra.
  2. OTel spans (Strands emits these for free) → self-hosted Langfuse or
     Phoenix — real trace visualization, no vendor lock-in.
  3. Same OTel → managed backend (Datadog/CloudWatch) — adds invoice
     reconciliation + pre-built eval dashboards, real $ cost.
  4. + LLM-judge evaluators over every trace — only worth it at real
     scale; flagged as carrying real technical debt.

**Not yet decided**: which tier to start on. Given the team's "simple is
best" motto, tier 1 or 2 is the obvious starting range, and tier 2 is
cheaper than it sounds since Strands already emits the spans — adopting it
would mean pointing an OTLP exporter at a self-hosted Langfuse/Phoenix
rather than writing instrumentation by hand. Still needs actual team
discussion before committing.

## 2026-08-09 — Subtasks Planner — scope, Task Broker boundary, structured_output correction

## Context

Continuing from the 08-06 session (Tool Execution Method). Working through the
next Aug-13 task, **Subtasks Planner** — "breaks the received tasks into
subtasks classified by the capability of each subagent." Most of this session
was resolving what that sentence actually means before writing any code.

## Decisions

- **Task Broker Agent (Mariam's card) vs. Subtasks Planner boundary,
  resolved**: reading Task Broker Agent's and Analyst Agent's actual card
  notes surfaced an apparent conflict with the already-built `SubagentMission`
  contract (subagent self-executes its own tool calls) — Task Broker's notes
  read as "execute the tools ... gather the raw events ... dispatch the
  results to the subagent to analyze," which sounded like *it* calls tools
  and subagents only analyze pre-fetched data. Confirmed with the user: that's
  not the intent. The actual division of labor:
  1. Analyst Agent → `AnalystTask` (tool-agnostic: goal + scope only).
  2. **Subtasks Planner** (this task) → classifies the task into
     `SubagentMission`s, one per relevant `ToolFamily`. Owns *only* this
     decision.
  3. **Task Broker Agent** → for each mission's `ToolFamily`, resolves
     "available tools to use" by querying the MCP gateway live. This is the
     dynamic equivalent of what `tools/registry.py`'s static `FAMILY_REGISTRY`
     does today.
  4. **Subagent** → builds its own `Agent(tools=<resolved tools>)` and
     self-executes, per the existing `SubagentMission` contract and the
     08-06 Tool Execution Method decision. Unchanged.
- **`AnalystTask` added as a new contract** (`contracts/analyst_task.py`) —
  the Analyst's "Task description" (question/goal + entity + time window,
  explicitly no product/index/field names) didn't have a type yet. Modeled as
  `task_id` + `hypothesis_id` + `goal` + `scope: Scope` — reuses `Scope`
  rather than inventing new entity/time-window fields.
- **Classification is LLM-driven, not rule-based** — decided explicitly, not
  defaulted to. A rule table would need typed entities (e.g. `file_hash`,
  `host`, `ip`) to key off, and that depends on Yousef's **Context Contract
  Template**, which doesn't exist yet and has no committed date. Rather than
  block this task on someone else's undelivered schema, `TaskClassification`
  (forced structured output: `tool_families: list[ToolFamily]`, `rationale:
  str`) is classified from the task's `goal` text directly. Revisit if/when
  typed entities land — a rule table would be cheaper and worth swapping in
  then.
- **Empty `tool_families` is a valid classification result**, not an error —
  the task may be unworkable for every domain the system currently knows
  about. Distinct from `SubtaskStatus.rejected`, which is a subagent's verdict
  on a mission it actually received; the Planner just emits zero missions.
- **Correction to the 08-06 session doc**: it said `structured_output()` "has
  its own automatic retry-on-validation-failure loop, independent of
  model-call retries." Checked against the actually-installed
  `strands-agents==1.50.2` source (not just docs, which didn't have this
  detail):
  - `Agent.structured_output()` / `structured_output_async()` are
    **deprecated** as of this version — both raise a `DeprecationWarning`
    pointing at the `structured_output_model` parameter on `Agent.__call__()`
    / the `Agent` constructor instead. `planner.py` uses the current API.
  - Structured output is implemented as a **forced tool call**
    (`StructuredOutputTool`, `tool_choice={"any": {}}`). A validation failure
    doesn't trigger a distinct retry subsystem — it comes back as an ordinary
    tool `status: "error"` result, and **the model's own loop decides whether
    to retry**, same as recovering from any other tool error. No fixed retry
    cap specific to structured output.
  - Token usage lives on `AgentResult.metrics.accumulated_usage`, a dict with
    **camelCase Bedrock/Converse-style keys** (`inputTokens`, `outputTokens`,
    `cacheReadInputTokens`, `cacheWriteInputTokens`) — not the snake_case
    `Usage` shape `Budget` already uses. `accumulated_usage` is cumulative
    over the `Agent` instance's *entire lifetime*, not just the last call, so
    reusing one long-lived planner `Agent` across rounds would leak prior
    calls' usage into every later `Budget.settle()`.

## What we built

- `contracts/src/contracts/analyst_task.py` — `AnalystTask`, `TaskClassification`.
- `contracts/tests/test_analyst_task.py` — valid/invalid construction, empty
  `tool_families` accepted, no-tool-specific-fields regression guard (same
  pattern as the existing `SubagentMission` guard).
- `backend/src/smartops/planner.py` — `plan_missions()`:
  - Reserves budget under `role="planner"` before calling the model; returns
    `[]` immediately (no model call) if the reservation fails.
  - `default_classifier(model)` constructs a **fresh `Agent` per call** —
    the fix for the accumulated-usage lifetime issue above.
  - `_usage_from_accumulated()` is the one place that translates Strands'
    camelCase usage dict into `Budget.Usage`.
  - `classify` is injectable (`Classifier` protocol) so tests never touch the

## Seven defects, every one found by running rather than reading

1. **Splunk TLS.** The cert is `CN=SplunkServerDefaultCert`, issued by
   `SplunkCommonCA`, with **no subjectAltName**. Two independent failures: no
   public trust store carries that CA, *and* with no SAN there is nothing for
   hostname verification to match against an IP, since Python dropped CN
   fallback. Importing the CA is necessary and insufficient. `MCPServerConfig`
   has no TLS fields at all, so trust cannot be expressed in `mcp_servers.json`
   — but `streamablehttp_client` accepts an `httpx_client_factory` and
   `MCPClient` takes a transport callable, so building the client ourselves is
   the supported seam. No patching.

2. **All botsv3 data is one day: 2018-08-20.** The CLI could only build windows
   ending at *now*, so every search returned zero events — indistinguishable
   from an empty domain. A benchmark built on that would have scored 0% and
   taught us nothing. Hence `--since` / `--until`.

3. **Verbose subagent answers crowded the Broker's output ceiling**, so the run
   ended before emitting a `TaskClassification`. `_digest()` now trims and says
   it trimmed; the full text still reaches the aggregator.

4. **The Broker re-dispatched `siem` three times**, spending 85% of the budget.
   `MAX_DISPATCHES_PER_FAMILY = 2`.

5. **`Limits(output_tokens=)` is cumulative across the loop**, not per call. A
   dozen SPL queries as tool arguments starved the final answer. Raised, and
   `stop_reason` is now surfaced wherever structured output goes missing —
   Strands ends a capped run with a stop reason and raises nothing, so "out of
   turns", "out of tokens", and "the model didn't answer" were one symptom
   needing three different fixes.

6. **`UnicodeEncodeError` destroyed a finished investigation.** Windows cp1252
   could not encode the model's answer, so `_print_outcome` raised *after* the
   work was done and billed. The findings existed, were paid for, and were
   replaced by a stack trace.

7. **`telemetry.py` was dead code.** `trace_attributes_for()`,
   `record_cost()`, and `record_result_status()` had no call sites. Traces
   carried Strands' generic spans with no task_id, no cost, no status — while
   every test passed, because a helper tested in isolation cannot reveal that
   nothing calls it.

## 2026-08-11 — Task Broker Agent — Broker-is-an-agent correction, typed entities, first executing integrations

## The correction that reshaped this session

The 08-09 entry describes the Broker as resolving tools for missions the
Subtasks Planner has already classified. Mohammed corrected the premise:

> "who said the broker will be deterministic? it's an agent and the subagents
> below it is a multiagent flow."

That was never a design detail to be assumed — it was his call, and an earlier
"direction verdict" asserted the opposite without asking. Worse, the research
backing that verdict had already found that *every* documented Strands
orchestrator is an LLM agent and that no plain-code supervisor pattern exists
anywhere in their docs. That finding was written down as a caveat and worked
around instead of surfacing it as a question.

**Supersedes** the 08-09 entry's Planner/Broker division of labour (points 2 and
3 of its "actual division of labour" list). Points 1 (Analyst → `AnalystTask`)
and 4 (subagent self-executes) still stand.

## Decisions

### The Broker is an LLM agent, and its tool choice *is* the classification

`plan_missions()` is retired rather than kept alongside the Broker. Running a
classification call and then having an agent decide which domains to engage is
two LLM calls making the same decision. The Broker's choice of which tool to
call **is** the classification; `TaskClassification` survives as the audit
record, now emitted by the Broker.

Its tested machinery was ported, not discarded: `_usage_from_accumulated()` (the
one bridge between Strands' camelCase usage keys and our snake_case `Usage`), the
injectable-Protocol test seam, and the reserve/release/settle discipline all
moved into `broker.py`, with their tests.

### Agents-as-Tools, using the `@tool`-wrapper variant

Strands documents three ways to do Agents-as-Tools. We use the third —
a `@tool` function constructing an `Agent` internally — which the docs offer
"for specialized control". The reason is concrete, not stylistic:
`Agent.as_tool()`'s tool spec is a single `input: string` and it returns text,
so `SubagentMission`, `Scope` validation, and `SubtaskResult`'s citation→evidence
checks cannot pass through it. A single `as_tool()` instance also refuses
concurrent invocation, returning a tool *error*.

**Not Swarm.** Read against the installed source rather than the docs summary:
`Swarm._build_node_input()` prepends to every node's prompt the original task,
the full handoff chain, and **every prior agent's shared context inlined
verbatim**. For SOC data that is disqualifying — our `Evidence` contract says raw
tool output is never shown to an LLM directly, and `SharedContext.add_context()`
has no such boundary. It also serialises (handoff transfers control) where we
want concurrent fan-out, and it owns the loop, leaving nowhere to wrap each node
in reserve/settle plus `SubtaskResult` assembly.

**Not Graph.** `GraphBuilder.add_node()` fixes the node set before `build()`, so
a per-task family set means rebuilding the topology every task to reimplement
what `ConcurrentToolExecutor` already does.

**Mid-run discovery needs no new machinery.** Mohammed asked what happens if a
subagent finds mid-run that another domain is needed. An agent calling a second
tool after seeing the first result has already re-dispatched — that is just the
agent loop. Only the signal was ours to build: `gaps: list[ToolFamily]`. It is
hub-and-spoke rather than peer-to-peer, deliberately: the Broker is the only
place holding the budget, the audit record, and the scope boundary.

### Typed entities — and this answers a question we were waiting on

`Scope.entities` was `list[str]`; it is now `list[Entity]` with
`EntityKind = Literal["host","user","ip","file_hash","domain","url","process"]`.

This is the shape the 08-09 entry was waiting on Yousef's Context Contract
Template to define, and the reason it mattered: a family's *dispatchability*
becomes a fact rather than a judgement. VirusTotal cannot be queried without a
hash, IP, domain, or URL, regardless of what any model decides. The mapping
lives in `broker.py`, not `contracts` — that module holds shape only, and
dispatchability is dispatch logic.

It is **not** a second classifier. `plan_missions()` was retired for duplicating
a *judgement*; this is a *precondition*, and it maps onto
`SubtaskStatus.REJECTED`'s documented meaning exactly.

Done now because it was cheapest now: `Scope.entities` was read by zero source
files and no Analyst populates it yet. The blast radius only grows.

### Two contract traps worth remembering

**`gaps` had to land on both models.** `SubtaskResult.from_answer()` splats
`**answer.model_dump()`, and pydantic's default `extra="ignore"` **silently
drops** unknown keys rather than raising. A field on `SubagentAnswer` alone would
have vanished between the subagent and the aggregator with no error. A test pins
it, because nothing else would catch it regressing.

**`REJECTED` must not set `error`.** `_StatusErrorContract` raises if `error` is
set on any non-`ERROR` status, so a rejection reason goes in `summary`. The first
draft of the stub subagent would have crashed on construction.

### The pricing bug that disabled budget gating

`ModelPrice` stored USD per million tokens, leaning on the coincidence that this
equals micro-USD per token. That holds only for whole-dollar rates. Every Claude
tier is $1–$25/Mtok so it never showed — but DeepSeek is sub-dollar and its input
rate truncated to `0`.

The ledger reporting input as free was the lesser problem. `estimate_cost()`
feeds `reserve()`, so a zero input rate made the admission check treat
input-heavy calls as costless and **budget gating silently stopped working** — on
the cheapest provider, which is exactly where a ceiling is most likely to be
relied on.

Rates are now nano-USD per token, which spans $0.014–$25/Mtok exactly, so one
table prices any provider and a cross-provider cost comparison is meaningful
rather than a comparison against zero. The 16 existing budget assertions needed
no changes: they assert on `cost_of()`'s micro-USD result, which did not change.

Cache pricing stays as *multipliers* on the base input rate, which is
Anthropic-shaped — some providers publish an absolute cache-hit price. Recorded
as an approximation rather than modelled, since nothing sets `cache_control` yet.

### MCP servers come from config, not code

Splunk is reached over MCP, which justified adopting `MCPClient.load_servers()`.
It deleted more than it added: credential interpolation, transport detection,
pagination, connection startup, internal caching, and per-server failure
isolation are all Strands'. Gone: `_started_clients`, `_clients_for()`, manual
`.start()` sequencing, and `tools/mcp/splunk.py`'s `NotImplementedError` stub.

What stays ours is the only thing Strands has no concept of: which servers serve
which `ToolFamily`. Clients are built per family by slicing the config rather
than correlating `load_servers()`'s flat, name-less return by position — which
would pair the wrong client to the wrong family whenever a server is skipped.

Every entry sets `continue_on_error`, which makes the no-credentials path work by
construction: an unset `${SPLUNK_TOKEN}` raises inside `load_servers()`, that
server is skipped, and `siem` resolves to zero tools instead of the process
failing.

### Enrichers: families that need no model

Some families need a decision about *what* to ask — which SPL to run, which host
to pivot to — and wait for a real subagent. A reputation lookup does not: the
entity's kind selects the endpoint and its value is the argument.

`ENRICHERS_BY_FAMILY` names that distinction, and it is what lets `vt` return
real `Evidence` with resolving citations **today**, with no model and no
subagent. Status reflects what was found rather than that the call worked: `OK`
when an indicator is flagged, `NO_DATA` when everything is clean or unknown.

VirusTotal is a native `@tool` rather than `strands_tools.http_request`: that
tool's four auth types emit `Authorization: Bearer|token|<raw>` or `X-API-Key`,
and VirusTotal accepts only `x-apikey`. The header *can* be passed as tool input
— but tool input comes from the model, so the key would land in the prompt, the
history, and any span recording tool inputs.

### Provider selection is configuration, not failover

`SMARTOPS_LLM_PROVIDER` → Bedrock (if `AWS_REGION`) → DeepSeek (if
`DEEPSEEK_API_KEY`) → scripted invoker. DeepSeek is wanted for cost; Bedrock is
the primary.

Resolution happens at **startup, from config**. A Bedrock outage does not fall
through to DeepSeek mid-run: retrying a failed call on another provider would
silently change which model, and which price, served a request. `ModelChoice`
carries `provider` because `build()` must return a bare id for Bedrock (Strands
constructs the model) and a constructed `Model` for anything OpenAI-compatible,

## The contract change

`SubagentAnswer.summary` was the only field findings could go in, so prose was
the only available shape — and prose became narrative, which became a conclusion
that belongs to the Analyst. That is why the 2026-08-11 run named `chrome.exe`
PID 9752 as cryptomining.

Two layers now. The model authors `queries_run` and a small `assessment`; **code**
assembles `findings` from what the tools actually returned. Neither half can forge
the other: a model that never sees the rows cannot invent them, and code that
never reads the prompt cannot be talked into re-categorising.

SIEM findings adopt **Splunk CIM names** — Network Resolution, Network Traffic,
Endpoint→Processes, Authentication. The bucket comes from the category the model
tagged its *own query* with, which it knows without inspecting a row, so there is
no per-sourcetype parser to drift from Splunk's field semantics.

## Four traps found, all verified against installed 1.51.0

Each would have failed later and more expensively than it did.

1. **A parameterized pydantic generic cannot be handed to
   `structured_output_model`.** Strands names the structured-output tool from
   `model.__name__` with no sanitisation, so `SubagentAnswer[SiemAssessment]`
   produces a tool name containing brackets — and Bedrock requires
   `^[a-zA-Z0-9_-]{1,64}$`. This fails at the provider, not in tests.
   `make_answer_model()` builds a concrete per-family model instead
   (`SiemAnswer`, `VtAnswer`, …), mirroring `make_investigate_tool()`.
2. **`findings` and `assessment` both need `SerializeAsAny`.** With a plain base-class
   annotation, pydantic dumps only the base's fields — verified: a populated
   subclass serialises to `{}`. Silently. Every row would have vanished on the way
   to `BrokerReport`, and the A/B would have compared empty payloads.
3. **`from_answer()` could not keep splatting `**answer.model_dump()`.** That worked
   only while both models carried identical field names; with `assessment` on one
   and `findings` on the other, `extra="ignore"` drops the mismatch silently — the
   same failure the `gaps` docstring has warned about since the contract was
   written. It now maps fields explicitly.
4. **`summary` was doing two jobs and only one was the problem.** Exactly one call
   site was model-authored; the other fifteen were code-authored status reasons
   like "no vt-queryable observable in scope". Those moved to `reason`, which is
   code-only and **required for `REJECTED`** — an unexplained rejection is
   indistinguishable from a bug.

## Two deliberate additions beyond the spec

Both are honesty mechanisms, and both are worth keeping or arguing with explicitly:

- **`SiemFindings.uncategorised`.** Not a fifth CIM category. When the model's
  reported query stops matching the one it actually ran, the rows land here rather
  than being dropped — they were retrieved and paid for, and a full bucket is a
  signal that reporting has drifted from behaviour.
- **The digest sends counts, not content.** `_digest()` now renders row counts per
  category plus the code-authored `reason`. Putting retrieved rows back into a
  model's context is exactly what the two layers exist to prevent, and there is a
  test asserting no row reaches it.

## The evidence collector was recording failures as findings

`_EvidenceCollector._record` guarded with `isinstance(event.result, BaseException)`.
That branch is **dead code**. `AfterToolCallEvent.result` is always a `ToolResult`;
failure travels on a separate `exception` field. Every failed tool call was
therefore recorded as `Evidence`, contradicting the method's own docstring.

Checking `exception` alone — the obvious fix, and the one first proposed — would
still have missed the case that matters here. An MCP tool failure maps `isError`
to `status="error"` and **raises nothing**, which is what every failed Splunk or
VT call looks like. Both are now checked, and the MCP case has its own test
precisely because it is the one a plausible fix gets wrong.

This mattered more than hygiene: Plan B §2 projects `findings` from `Evidence`,
so the defect would have been baked into the new contract.

**The tests had encoded the bug.** `test_a_failed_tool_call_is_not_recorded_as_evidence`
built an event carrying an exception *as its result* — a shape the SDK never
produces — so the test proved the code matched a fiction. `_Event` now mirrors the
real event and the case is split three ways.

## The deprecation guard, and why the obvious version would not have worked

The `invocation_state` defect was easy to fix and hard to *notice*: Strands warns
on every Broker invocation and no `filterwarnings` was configured anywhere.

The obvious guard — `error::DeprecationWarning` scoped to the `strands` module —
**would have caught nothing**, for two independent reasons found by reading the
installed source:

1. Strands is inconsistent about categories. Most calls pass `DeprecationWarning`,
   `models/bedrock.py` passes `UserWarning`, and the two `**kwargs` deprecations
   pass **no category at all**, defaulting to `UserWarning`. The exact warning
   that motivated the guard was in the missed set.
2. Strands warns with `stacklevel=2`, so the warning is attributed to *our*
   calling module. A `:strands.*` module filter matches nothing.

The config covers both categories and is deliberately unscoped, with that
reasoning recorded in `pyproject.toml`. Baseline was zero warnings, so nothing is
being suppressed.

**The guard is asserted, not assumed.** `TestDeprecationGuardIsArmed` fails when
the filter is overridden with `-W ignore::UserWarning -W ignore::DeprecationWarning`.
A filter that matches nothing reads as protection while providing none, which is
the failure mode worth testing for.

## The index guard

The 2026-08-11 run issued every SPL as `index=*`. The design spec had already
settled the fix as a `BeforeToolCallEvent` hook rather than prompt text, on the
principle that a precondition is not a judgement. Nothing had been built.

`smartops/guards.py:IndexScopeGuard` cancels a call whose search targets a
non-allowlisted index, and cancels a search that pins **no** index at all — an
unpinned search runs against whatever the token's defaults are. `cancel_tool`
carries the reason back as the tool result, which is the SDK's own idiom and
gives the model a chance to reissue rather than simply fail.

`index_allowlist` lives on `DomainSpec` because which index holds the data is a
deployment fact; `Scope` is the authorization boundary. `None` means the domain
has no index concept, distinct from an empty tuple forbidding everything. Only
`siem` declares one.

**Stated plainly, at the definition site: this is a correctness guardrail, not a
security control.** Deciding that an SPL targets only allowed indexes by string
inspection is not decidable in general — subsearches, macros and `tstats` reach
data by routes it never sees. It catches the observed failure and raises the cost
of an injected instruction; it does not stop an adversary who controls the query
string.

**The strong version costs no code and is not yet done: scope the Splunk token to
`botsv3`.** Then `index=*` returns only `botsv3` server-side regardless of what
any model writes. The hook stops a confused model; the token scope stops an
adversary. Worth doing independently.

Two properties are pinned by test rather than assumed:
- The guard is driven through a **real `HookRegistry`** with the real event type,
  so a change to the hook protocol fails the suite instead of silently disarming it.
- A cancelled call arrives as `status="error"`, so the corrected collector will
  not record a blocked query as `Evidence`. The two changes were made for
  unrelated reasons; their composition is tested, not hoped for.

No path bypasses it. `--scripted` replaces the *Broker's* model only; the subagent
still builds an `Agent` with hooks, and with no model configured the stub subagent
makes no tool calls at all.

## The MCP diagnosis was wrong, and the wrong version was written down

**What was recorded:** `MCPClient` is a `ToolProvider` with ref-counted
consumers, so the first subagent's `Agent.cleanup()` drops the count to zero and
closes the connection under a second dispatch. Fix: hold a process-level
consumer across the run.

**Why it is wrong:** `add_consumer` and `remove_consumer` have exactly one call
site each in the whole SDK — `strands/tools/registry.py:133`, inside the
`isinstance(tool, ToolProvider)` branch of `ToolRegistry.process_tools`, and
`:700`, iterating `_tool_providers` from `ToolRegistry.cleanup()`. `tools_for()`
resolves the client itself and hands `Agent` a list of `MCPAgentTool`s, which
match the earlier `AgentTool` branch at `:121`. The client never enters
`_tool_providers`. No consumer is ever taken, so none is ever released, and the
zero-consumer teardown at `mcp_client.py:476-484` is unreachable. **A
process-level consumer would have fixed nothing** — nothing was releasing one.

**What the artifact says.** In
`.smartops/runs/botsv3_coinhive/20260815T124556942/report.json`, `results` holds
three entries in this order:

| # | task_id | status | queries | evidence |
|---|---|---|---|---|
| 0 | `…:siem:tooluse_Jrl1MJte…` | rejected | 0 | 0 |
| 1 | `…:vt:tooluse_xPjf91Yj…` | ok | 1 | 2 |
| 2 | `…:siem:tooluse_obxSwKkI…` | ok | 11 | 24 |

The rejected siem dispatch finished **first** and did nothing. A teardown under
the second dispatch predicts the opposite order, and the sticky
`_connection_failed` flag (`mcp_client.py:401-403`) would have failed the second
one too.

**What it actually was.** Strands runs a turn's tool calls under
`ConcurrentToolExecutor` by default, so a plan with two `siem` steps sends both
into `tools_for("siem")` at once — each on its own thread, since
`_load_tools_off_loop` uses `asyncio.to_thread`. `MCPClient.load_tools()` checks
`_tool_provider_started` and only then calls `start()`
(`mcp_client.py:405-409`), with a network handshake in between and no lock
across the two; `_is_session_active()` goes true as soon as `Thread.start()`
returns, before the handshake completes. The loser called `start()` on a
starting client, got `MCPClientInitializationError("the client session is
currently running")` (`mcp_client.py:334-336`), and `continue_on_error: true`
converted that into `_connection_failed = True` and `[]`
(`mcp_client.py:411-417`).

Reproduced deterministically before fixing, against unmodified code: first
caller `['splunk_search']`, second caller `[]`, sticky failure set.

**Fix.** `warm_mcp_clients()` resolves every built client once at startup, called
from `main._run()` and `bench._run()`, so no dispatch ever reaches the racy
branch. `_load_tools_off_loop` also takes a per-client lock, so the property
holds for a caller that never warmed — forgetting to warm is exactly how this
failed the first time, and warming being the *only* defence would leave a third
entry point free to reintroduce it. `PROCESS_CONSUMER` is claimed on each client
as well; it does not fix this, and says so in its own docstring, but it closes
the teardown path before someone passes a client straight into
`Agent(tools=[...])`.

**Ruling:** a mechanism that has been read in the SDK beats a mechanism that
merely explains the symptom. The wrong version had been written into a docstring
(`registry.py`), the architecture document, and the issue list, from where it
would have been re-derived indefinitely. Both now carry the correction and the
reason it was believable.

## A step is judged against the category it asked for

`CompletionRule` gains `categories: list[CimCategory]`. When set, `evaluate_step`
counts only those buckets from `_finding_counts()`. Empty — the default — counts
everything, which is the only sensible rule for `vt`, whose findings are not
bucketed this way.

This needed no new machinery: `CimCategory` is already exactly the field names of
the `SiemFindings` buckets (`contracts/findings.py:21`), which is what
`_finding_counts` already yields.

Two decisions inside it:

- **`uncategorised` never satisfies a named category.** It is the honesty bucket
  for rows the subagent never tagged. Letting it stand in for a category would
  rebuild the false-completion bug one layer up.
- **A category nobody retrieved into is not confirmed-empty.** `_finding_counts`
  reports a bucket that ran and returned nothing (it holds a zero-row
  `ResultSet`) and omits a bucket nobody touched, so presence is the code-side
  evidence that the question was asked. Without this, a step scoped to
  `dns_resolutions` whose subagent only returned process events would score as
  "we looked for DNS and it is not there" — the same false negative in a new
  place. "We queried DNS and found nothing" is a finding; "we never queried DNS"
  is a gap.

The Broker prompt now tells the planner to split `siem` by CIM category and set
`completion.categories` per step. The contracts already permitted this —
`DISPATCHES_PER_PLANNED_STEP = 2` under `MAX_PLANNED_DISPATCHES_PER_FAMILY = 6`,
and `DEFAULT_BROKER_TURNS = 11` was already sized for three siem steps. What was
missing was a reason to split and a way for code to judge the result.

**Unmeasured, deliberately.** Each step is its own mission, so its own system
prompt and tool schemas. `report.json` persists only `total_spend_micro_usd`, not
the ledger, so prompt-cache engagement could not be read back from the three
existing runs. If caching is not engaged this raises input cost. Needs `--runs 3`
before and after; the trade is evidence-first, not assumed.

## The index-scoping metric could not fail

`bench.check_index_scoping()` scored correctness by calling
`IndexScopeGuard._reject_reason` — the guard's own predicate — over
`queries_run`. Every query that actually executed passed that predicate by
construction, and `_EvidenceCollector._record` drops failed calls, so a
guard-cancelled query never reached `queries_run` either.
`index_scoping_correct_pct` was therefore ~always 100%, while the entire reason
it exists is the 2026-08-11 run in which every SPL was `index=*`.

- **It scores attempts, not successes.** `IndexScopeGuard` now records what it
  cancelled, `SubtaskResult.blocked_queries` carries it, and the metric counts
  it. A blocked query was previously invisible to everyone, including an analyst
  reading the report.
- **It no longer consults the guard.** The rule is implemented in `bench.py` so
  the two can disagree — which is the only condition under which measuring is
  worth anything. Pinned by a test that makes `_reject_reason` raise.

Also: the `IndexScopeGuard` docstring still claimed the rule was "require a
literal allowlisted `index=` on anything that is a search". The code had been
relaxed to accept a CIM predicate instead, and since `_LOOKS_LIKE_SEARCH` matches

shape the siem prompt tells the model to write. The docstring now states the
three real rules and says plainly what rule 2 concedes. `_CIM_PREDICATES` moved
to module level, where every other pattern in that file lives.

### Root cause, measured directly

```
edr  | servers= 0 | tools= 0
ndr  | servers= 0 | tools= 0
```

`tools_for("siem")` returns **zero tools** and `server_count("siem")` is **zero**,
with `.env` loaded — the Splunk MCP client is never constructed by
`smartops.tools.registry`. `vt`'s 4 tools are native and need no MCP server, which is

So the smoke run measured **VirusTotal lookups plus broker overhead**, on both arms.
Splunk — the domain the entire case is about, holding 2,030,269 events — contributed
nothing to either arm.

### The actual cause: TLS certificate verification, not availability

Reproduced directly with `MCPClient.load_servers('mcp_servers.json')` after loading
`.env`:

```
SPLUNK_MCP_URL set: True
servers in config: ['splunk', 'edr', 'ndr']
clients built: 1
  ERROR MCPClientInitializationError: the client initialization failed
httpx.ConnectError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
  self-signed certificate in certificate chain (_ssl.c:1032)
```

**Splunk is not down.** The host answers and the TLS handshake begins — it is
rejected because the server presents a **self-signed certificate** that httpx will
not verify. Client construction then raises `MCPClientInitializationError`, the
registry swallows it, and `server_count("siem")` reports 0. Every layer above sees
"this domain isn't available" and reports honestly on that basis.

Note the correction: an earlier subagent claimed it had loaded 10 tools including
`splunk_run_query` through this same path. **Treat that as unreliable** — it is
contradicted by this reproduction, and that agent had already been wrong once today.
It most likely used a raw `httpx` call with verification disabled.

Also visible above: only **1 of 3** configured servers is built at all. `edr` and
`ndr` produce no client, presumably missing their env vars — consistent with both
scoring zero spend in the smoke run.

**This is blocker #1. Nothing about the A/B means anything until it is fixed.**

#### Where the TLS seam actually is — verified in the installed packages

- `MCPClient.load_servers()` **cannot** be configured for TLS. At
  `strands/tools/mcp/mcp_client.py:1715` it builds the transport as
  `streamablehttp_client(url=..., headers=headers)` — url and headers only. There is
  no hook. **This is the path `registry.py` uses today, which is why the certificate
  cannot currently be trusted through configuration.**
- The underlying transport **does** expose one:
  `mcp/client/streamable_http.py:686-693` declares
  `httpx_client_factory: McpHttpClientFactory = create_mcp_http_client`.

So the fix is to stop routing this server through `load_servers()` and construct its
`MCPClient` with an explicit transport callable:

```python
MCPClient(lambda: streamablehttp_client(
    url=url, headers=headers,
    httpx_client_factory=<factory returning an httpx client with the right verify=>,
))
```

**Prefer `verify="<path to the Splunk CA/cert>"` over `verify=False`.** It is the
same size of change and keeps MITM protection; `verify=False` on a SIEM connection
means anything on the path can feed this system fabricated security telemetry, which
is a worse failure than the one being fixed. If `verify=False` is used anyway, gate
it behind an explicit, named, lab-only env flag that defaults to off and logs loudly
on every run — never a silent default.

Do **not** assume `SSL_CERT_FILE` / `REQUESTS_CA_BUNDLE` will fix this without
testing: httpx builds its default context from certifi, and whether those variables
are honoured depends on how the context is created. Verify before relying on it.

Second-order issue worth fixing alongside it: **the registry turns a construction
failure into silence.** A certificate rejection and "no server configured" are
opposite problems and currently look identical from `tools_for()`. That is what let
a whole live run proceed and report success while the primary domain was absent.

### Second finding, confirmed live: `dispatched` means different things per arm

```
F | dispatched=['vt']                    | findings={'vt_verdicts': 2}
```

## Standing architectural threads

Raised and deliberately left open, not decided:

- **Multi-hypothesis investigations.** Direction set, not designed: the Broker
  *should* see the hypotheses (plural — competing benign/malicious
  explanations), each gets its own end-to-end run, parallel where possible, and
  the domain analysts still never see any hypothesis. This does not contradict
  the recorded decision — `contracts/reasoning.py` excluded hypothesis prose
  *"until a consumer needed them"*, and the Broker is now that consumer. The
  selection-bias risk it introduces is mitigated by the plural itself: fetching
  to *discriminate between* competing explanations forces broader retrieval than
  confirming one.
- **`hypothesis_id` is a dead constant** — `main.py:558` hardcodes
  `"cli-hypothesis"` on every CLI run. Any hypothesis store starts here.
- **`combine()` is pre-built Analyst Agent territory.** It already implements a
  thin version of the Aggregator that the Analyst Agent epic (Mariam's, unbuilt)
  claims as its own responsibility. Worth flagging so it is absorbed or replaced
  deliberately rather than rebuilt blind.
