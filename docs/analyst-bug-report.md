# Analyst Bug Report

**Scope:** two sections.
- **Integration attempt: code and logic** covers the integration release `d113695` (2026-09-20): the environment, the connections and the alert context it built for the Analyst.
- **Analyst: code and logic** covers the **main Analyst Agent** (Foundation-Sec-8B plan and synthesis in `webapp/main.py` and `webapp/prompts/`).

The Tool Broker and its identity/network/endpoint sub-analysts are out of scope and tracked separately.

**Source runs:**
- "SmartOps SOC2", 2026-09-29. Alert: *Custom – Windows PowerShell Ingress Tool Transfer*, host `ar-f6eddb5b-df6`, user `Administrator`. 1 planning loop and 11 broker/synthesis loops.
- `cecd266a`, 2026-09-30: the first run after the integration fixes, so the Analyst received real Broker evidence. Alert: *Threat - sama- ESCU - Malicious PowerShell Process - Encoded Command*, same host and user. 1 planning loop and 1 broker/synthesis loop. Trace: `.smartops/runs/cecd266a/investigation.jsonl`.

**Status as of 2026-09-30:** C1–C3 are removed from the code ; the credentials still need rotating. C4 is open. C5 is partly resolved. C6 is partly fixed: `event_time` uses the notable's `_time`, which is the detection time, not the activity time. A1–A8 are open. A9's causes are C6 (partly fixed), A10 (fixed) and A11 (open). A6 recurred in run `072fd610`: tasks T5 (`service`) and T8 (`command`) were dropped for unsearchable entity kinds. The `.smartops/runs/…` paths are local run artifacts; ask for them if you need them.

## Integration attempt: code and logic (release `d113695`, 2026-09-20)

These are not Analyst reasoning bugs. They sit under the Analyst's runtime environment and inputs, and C1–C3 are the most severe findings in this report. The release was a single parentless commit authored as "SmartOps SOC", so it bypassed review, and git can't attribute individual changes.

| # | Bug | Cause | Error it causes |
|---|---|---|---|
| C1 | **Live secrets committed in plain text.** `start_server.bat` is tracked in git and sets `FS8B_API_KEY` (Bedrock), `VT_API_KEY` and `SPLUNK_TOKEN` (a JWT), plus `FS8B_MODEL_ARN` (which exposes the AWS account ID). **Pushed:** it has been on `origin/main`, `origin/integration` and `origin/feature/task-broker-input` since `d113695`. The Bedrock key is the one the Analyst uses today. `start.ps1` was checked too and holds no secrets (it reads `.env`). **2026-09-30:** the secrets are removed from `start_server.bat` in the working tree ; the webapp loads `.env` at startup. | Launch configuration hardcoded into a tracked script instead of read from the git-ignored `.env`. | Anyone with repo access can bill the Bedrock model and use the VirusTotal and Splunk identities. **Rotate all three.** Removing the file from the tree doesn't remove it from history. |
| C2 | **Hardcoded Splunk username and password** (user `ysalah`; the password is not repeated here) as defaults in `local_splunk_mcp.py:15-16` and `webapp/main.py:150-151`, plus a default OpenCTI token (`webapp/main.py:81`). Line numbers are as of `d113695`. All pushed. **2026-09-30:** `local_splunk_mcp.py` is deleted and the defaults are removed . | Credentials used as fallback values in code. | The Splunk account is exposed to anyone with repo access. **Rotate the password** and the OpenCTI token; they remain in git history. |
| C3 | **The official Splunk MCP server was swapped for a makeshift wrapper.** `mcp_servers.json` stopped pointing at the Splunkbase MCP Server (`${SPLUNK_MCP_URL}` with a bearer token, 17 tools including `splunk_run_query` with `earliest_time`/`latest_time`) and launched `local_splunk_mcp.py` instead. That script logs into Splunk Web over an ngrok tunnel and exposes 3 tools. | The integration replaced the configured MCP connection rather than using it. `.env` still points at the official server, which is live. | Every query the Analyst's evidence depends on degrades:<br>• no time window (43 of 45 queries unbounded);<br>• results returned as strings, so the broker projects 0 rows;<br>• errors returned as normal output, so a failed search reads as "looked, found nothing";<br>• no index or sourcetype discovery;<br>• search only works while the tunnel is up (it was offline on 2026-09-29).<br>**Resolved 2026-09-30:** `mcp_servers.json` points at the official server again (verified live: 17 tools). |
| C4 | **Wrong index in the alert context.** The seed says `source_context.index = win_sysmon`, but that index doesn't exist. The host's events are in `windows_lab` (`XmlWinEventLog`, 4,131 events in the alert window). | The index is hardcoded as `"win_sysmon"` in `webapp/static/app.js:81` and `:104`, not read from the alert or from Splunk. Still open. | The Analyst plans against an index that holds nothing, and a broker allowlist built from the seed would block the real one. |
| C5 | **The ESCU corpus is missing from the repo.** In `d113695`, `webapp/main.py` loaded `bm25_corpus.json` from the repo root. It was never committed, in any branch or in history. On a fresh checkout the webapp logs "Could not load bm25_corpus.json" and `/api/escu` returns `ESCU corpus not loaded`. | A runtime data file lived only on the integrator's machine. The copies in other local projects (PulseSec, SAMA, sama2.0) have different schemas (3–6 fields per rule). The corpus the SOC2 run used carried the full ESCU detection fields, so it is none of them. Also, the SOC2 run's ESCU response put `spl` beside `data`, a shape the repo's `/api/escu` code doesn't produce, so the webapp that ran it wasn't this code. | The Analyst loses its reference rule: no ESCU match, so no reference SPL for the alignment judgement (see A7) and no rule description, data sources or known false positives in its context. **Resolved 2026-09-30:** the corpus was supplied at `docs/corpus/bm25_corpus.json` (2,075 rules: `name`, `spl`, `data_source`, `known_false_positives`, `analytic_story`, `mitre_attack_id`), and `webapp/main.py` now loads it from there. That gives the Analyst the reference SPL back, but not the richer fields (`description`, `how_to_implement`) the SOC2 run saw. **Still open:** the matcher scores rule *names* only. With this corpus, the SOC2 custom PowerShell rule's top match is "Linux Ingress Tool Transfer Hunting", the wrong OS. |
| C6 | **The alert's `event_time` was the browser's current time, not the alert's.** `normalized_seed.event_time` was set with `new Date().toISOString()` in `webapp/static/app.js`, so on run `cecd266a` the Analyst received 2026-09-30 for an alert from `2026-09-27T14:53:35+03:00`. | The context builder stamped "now" instead of reading the imported alert's `_time`. `ingest_time` is set the same way, which is correct for that field. | With no usable alert time in the seed, the Analyst took the time from `raw_event_data` itself and mis-converted it. That's the root cause of A9. **Partly fixed 2026-09-30:** `event_time` is now the imported alert's `_time` in UTC (verified: `16:04:16+03:00` → `13:04:16Z`), or `null` when the alert has no time. **Still open:** a notable's `_time` is when the detection search fired, not when the activity happened. On run `072fd610` the notable's `_time` was `15:04:02+03:00`, but its own `firstTime`/`lastTime` fields say `2026-09-27T14:55:17` (Splunk local time, which is 11:55:17Z), 9 minutes earlier. The narrow task windows (`12:04:02Z–12:05:02Z`) missed the actual execution, and only the broad baseline tasks found it. `event_time` should come from `firstTime`, or from `orig_time`, when the notable carries them. `firstTime` has no offset, so it has to take the offset from `_time`. |

### Context pipeline (smaller items)
These are also part of the integration release. They feed the Analyst but are produced before it runs:
- `192.168.40.211` and the parent image path are never extracted as entities.
- The ESCU matcher's top hit is the `explorer.exe` rule, not the PowerShell one.
- OpenCTI looks up `powershell.exe` as a domain, and a `T1105` lookup returns other techniques.

## Analyst: code and logic

> **Caveat.** In the SOC2 run, integration bugs meant the Analyst never received evidence about this alert: every broker loop fed it the same 8-day-old run from a different alert. A2, A3, A4 and A8 may be partly symptoms of that empty input. Run `cecd266a` did receive real findings: A1 and A5 recurred in it, and A9–A11 were found in it.

| # | Bug | Cause | Error it causes |
|---|---|---|---|
| A1 | Synthesis returned `status: VERDICT_REACHED` with top score H1=35 (H2 25, H3 15), verdict UNCERTAIN, confidence 30% (loop 12). | `status` is self-reported by the model. The "top ≥ 85 and leads by ≥ 20" rule exists only in the prompt, and no code checks `hypothesis_scores` against it before the loop stops. | The investigation ends as "verdict reached" on an answer that, by its own rule, never reached one. The terminal state misreports the outcome.<br>**Recurred in `cecd266a`:** verdict FALSE_POSITIVE at 95%, yet the scores were H1 25 / H2 (FALSE_POSITIVE) 88 / H3 (BENIGN) 92. The top-scoring hypothesis isn't the verdict, and it leads by 4, not 20. The loop stops on `status` alone (`webapp/main.py:580`). |
| A2 | Scores swing on identical input. Loops 2→12 went 60/30/10, 60/75/65, 0/0/0, 45/30/35, 35/25/15, and the leading hypothesis flips between H1 and H2. | No defined baseline for "no evidence". The prompt says both "score strictly on how well the findings match" and "absence of evidence is not evidence of absence", on a 1–100 scale with no neutral point. | Scores aren't reproducible, so they can't be compared across loops or trusted as a stopping signal. |
| A3 | Runaway deliberation: 3,073 and 4,406 generation tokens (loops 3 and 6) spent debating whether a no-evidence score should be 1 or 50, and whether scores are required under REQUIRES_INVESTIGATION. | Same prompt conflict as A2, plus unclear schema requirements per status. | Cost and latency, and 4,406 is above the 4,096 `DEFAULT_MAX_GEN_LEN` in `webapp/services/llm_service.py`, so there's a risk of truncated JSON. |
| A4 | Alert text cited as evidence. Loop 12: "The evidence shows a PowerShell process downloading a file from a suspicious IP". No retrieved finding about this alert existed. | The hypotheses restate the alert's own details. The synthesis prompt doesn't separate alert facts from retrieved findings. | The verdict's reasoning rests on the unverified alert, not on investigation evidence. Circular confirmation. |
| A5 | Masquerade signal missed. The parent process is `C:\Users\Administrator\Desktop\splunkd.exe`, yet H2/H3 assume a legitimate Splunk component, and tasks T1/T3 ask whether this is a "legitimate Splunk update". | Reasoning keyed on the process name, not the image path. The questions are framed towards the benign hypothesis. | The plan is skewed towards benign, and no task checks the binary's path, hash or signature, which is the fastest discriminator for this alert.<br>**Recurred in `cecd266a`, this time with the evidence in hand:** the Broker returned process rows whose parent was `C:\Users\Administrator\Desktop\splunkd.exe` (10 rows) or `C:\Users\Public\splunkd.exe` (15), alongside the real `C:\Program Files\SplunkUniversalForwarder\bin\splunkd.exe` (82). The synthesis still concluded "all processes trace back to legitimate Splunk operations". |
| A6 | Invalid or wrong task entities. The section-5 plan's T3 uses `type: "command"`, which is not a valid entity kind (`host, user, ip, file_hash, domain, url, process`) and breaks the planning prompt's own `host\|ip\|user` schema (`webapp/main.py:339`). T2 calls `192.168.40.211` a "source IP", but it's the download server (destination). | Output isn't held to the allowed kinds, and direction isn't taken from the command line. | The broker contract rejects the task, and pivots get queried in the wrong direction. |
| A7 | SPL alignment judged ALIGNED between the PowerShell deployed SPL and an `explorer.exe` reference rule. Loop 3's reasoning calls the same alert NOT_ALIGNED. | Alignment judged on the shared technique (T1105), not on the process or field logic. Two separate Analyst calls reach opposite conclusions. | A false alignment signal reaches synthesis, and the two sources contradict each other. |
| A8 | Verdict/status vocabulary confused. Loop 5's reasoning concludes "the verdict is UNDECIDED", and loop 6 proposes `verdict = REQUIRES_INVESTIGATION`. | Status and verdict enums aren't clearly separated in the prompt. | Risk of an out-of-enum verdict in the emitted JSON. Check the field in the raw output. |
| A9 | **Task windows were in the wrong time zone, and the verdict rests on the wrong 40 seconds** (`cecd266a`). The alert time is `2026-09-27T14:53:35+03:00` (11:53:35Z). The plan's windows were `14:53:35Z–14:54:15Z`: the local clock time relabelled as UTC, 3 hours late. Those windows belonged to the three tasks about the command itself (T1–T3), and T6 (`14:50–14:55Z`) was offset the same way. Inside them, the Broker found only Splunk's own `splunk-powershell.exe`. The synthesis explained the "encoded" command by that process's `--ps2` flag and returned FALSE_POSITIVE. The broad tasks T4 (26–28 Sep) and T5 (all of September) did cover 11:53:35Z, and T5 returned the alert's `powershell.exe -EncodedCommand …` rows as Administrator. The synthesis didn't reconcile them with the narrow-window results. | Three causes, each listed as its own bug: the seed carried no alert time (**C6**, integration), the prompt gave no rule for windows (**A10**), and no code checks windows against the alert time (**A11**). | The tasks that target the alert's own moment search the wrong period, and the verdict leans on unrelated events. The `cecd266a` FALSE_POSITIVE should not be trusted. |
| A10 | **The planning prompt has no rule for deriving `time_window`.** The prompt the investigation loop uses, `webapp/prompts/system_prompt.txt`, shows the field only as `<ISO8601>`. The one anchoring rule ("one hour before/after {event_time}", `webapp/main.py:352`) is in the separate step-5 `/api/analyst` prompt, not in the loop. | Each prompt was written separately, and the rule was never carried over. | The model picks a time source and zone on its own. On `cecd266a` it copied `14:53:35` from `raw_event_data` and relabelled the `+03:00` as `Z` (A9). **Fixed 2026-09-30:** the loop's prompt now says to anchor every window on `normalized_seed.event_time` and write UTC with a `Z` suffix.  |
| A11 | **No code checks a task's window against the alert time.** A window that parses but is hours away from the alert passes straight to the Broker. | The only check (`webapp/services/run_trace.py`) drops malformed windows. It doesn't compare them with `event_time`. | A prompt rule alone can't guarantee A9 won't recur: nothing catches a model that ignores A10's rule. Still open. Suggested check: every plan and follow-up window must overlap `event_time` ± a set margin, or the task is dropped with a reason. |
